# Code-scanning dismissals: the governing rule

"0 alerts" is only worth something if anyone can later reconstruct how it was
reached: what was **fixed**, what was **dismissed**, and why. This rule governs
QZP and every repository QZP governs. It applies to CodeQL and to any other
SARIF producer that feeds GitHub code scanning (opengrep, zizmor, ...).

## The rule

1. **Fix beats dismiss.** A dismissal is the exception. It is allowed only for
   a demonstrable false positive or a genuinely by-design pattern, and never
   as a way to reach a green badge or an "always green" target.
2. **Every dismissal carries a written rationale** that names why the alert
   cannot be exploited *in that repository's context*: which input the
   finding is about, who controls it, and what it can reach. "Not
   exploitable" or "by design" on its own is not a rationale.
3. **Every dismissal is logged where it can be audited:**
   - QZP's own: a row in the [log below](#log-quality-zero-platform), in the
     same PR that justifies it or right after.
   - A governed repo's: a row in that repo's own
     `docs/CODE-SCANNING-DISMISSALS.md` (same columns), the per-repo receipt.
   The GitHub dismissal comment (280 characters at most) states the
   rationale's core and points at the log.
4. **A dismissal you would repeat across repos is a defect in the shared
   layer.** If the same alert would be dismissed in several repos, fix the
   template, the reusable workflow, or the query configuration once instead.

## Choosing the reason

GitHub offers three reasons. Use them for what they mean:

| Reason | Use it when | Never for |
| --- | --- | --- |
| `false positive` | The query is wrong about this code: the flagged flow cannot happen. Say why (for example, the trigger can never carry untrusted input). | Code that is merely "unlikely" to be reached. |
| `used in tests` | The code exists only to exercise a detector or fixer, for example a fixture of the anti-pattern a patch generator rewrites. | Workflow or production code. |
| `won't fix` | A real, understood risk that is accepted on purpose. This needs the strongest rationale, an owner, and a review date. | Anything that a reasonable change could fix. |

## How to dismiss

```bash
# 1. Add the log row first (repo docs/CODE-SCANNING-DISMISSALS.md).
# 2. Dismiss with the rationale's core (<= 280 chars) and the log pointer.
gh api -X PATCH repos/OWNER/REPO/code-scanning/alerts/NUMBER   -f state=dismissed   -f dismissed_reason="false positive"   -f dismissed_comment="<why it cannot be exploited here>. Logged: docs/CODE-SCANNING-DISMISSALS.md"
```

Reviewers reject a dismissal PR that has no log row, and a log row whose
rationale does not name the trust boundary.
